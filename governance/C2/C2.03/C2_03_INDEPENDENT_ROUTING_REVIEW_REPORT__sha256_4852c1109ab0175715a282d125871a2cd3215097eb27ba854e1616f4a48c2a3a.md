## 3. Blocking findings

### C2ROUTE-B01 — Load-bearing candidate-set and route-policy snapshot identity is not semantically closed

C2.03 correctly states that `candidate_set_ref` is an exact content-addressed candidate inventory and that `route_policy_snapshot_ref` identifies content-addressed C2 routing semantics. However, the candidate does not define the load-bearing semantic identity contract needed to resolve either object.

There is no `CandidateSetDefinition` record at all. `RoutePolicySnapshot` contains `route_policy_id`, `semantic_revision`, rules, and `external_gate_fallback_mode`, but no content-identity tuple or stable-ref-kind contract comparable to the C2.01R1 `C2StableSemanticRef` discipline. In addition, route-policy eligibility says a candidate must be “permitted by the pinned route policy snapshot,” but `RoutePolicySnapshot` defines no candidate permission/allowlist predicate or other deterministic permission relation.

Consequences:

1. a replay validator cannot independently prove that two `candidate_set_ref` values resolve to the exact same candidate inventory;
2. it cannot independently prove that a `route_policy_snapshot_ref` resolves to the exact same policy semantics;
3. the route-policy-eligible set is not derivable from the declared `RoutePolicySnapshot` model because “permitted” has no normative representation;
4. C2.07 would be forced to invent semantic identity/eligibility rules rather than merely encode C2.03 semantics.

**Required repair:** define content-addressed logical identities for `CandidateSetDefinition` and `RoutePolicySnapshot` (including exact immutable content identity and ref equality), define the candidate inventory members/uniqueness contract, and define exactly how route-policy permission is derived. Exact wire serialization may remain C2.07-owned, but semantic identity and permission must be frozen here.

**Affected acceptance IDs:** `C2-221`, `C2-226`.

### C2ROUTE-B02 — `ContinuationRule` matching is under-specified before deterministic tie-breaking

C2.03 deterministically orders already-matching rules by `(rule_priority, rule_id)`, but it never defines the exact predicate that determines whether a rule matches.

A rule has optional qualifiers:

```text
failure_family?
failure_code?
diagnostic_retry_hint?
```

The phrase “collect all exact matches” does not specify whether an omitted qualifier means wildcard / unconstrained, requires the attempt field to be absent, or has another meaning. Nor does the contract define whether a rule carrying `failure_code` without `failure_family` is legal, or how a retry-hint qualifier is compared.

Two conforming implementations can therefore construct different matching-rule sets for the same pinned attempt and policy snapshot, then both apply the same deterministic sort to different inputs and produce different route actions.

**Required repair:** freeze an exact rule-match predicate, including optional-field semantics, illegal qualifier combinations, exact enum/string equality, and fail-closed behavior for unknown values. Add adversarial vectors for a generic FAILED rule versus family-specific/code-specific/hint-specific rules.

**Affected acceptance IDs:** `C2-226`, `C2-227`.

### C2ROUTE-B03 — External-admission fallback lacks event-level provenance and deterministic candidate-consumption semantics

C2.03 correctly says that a non-positive external gate causes no provider dispatch and that a policy may nominate another candidate while preserving the load-bearing external gate reference. But the logical records do not provide a complete deterministic representation for that path.

`FallbackEvent` has no `external_admission_ref` / `external_admission_refs[]` field. `RouteAttemptRecord` can carry external-admission refs, but an externally blocked candidate produces **no dispatched attempt**, so there is no attempt record on which to attach the gate that triggered the fallback. `RouteResolution.external_admission_refs[]` is only a route-level aggregate and does not bind a particular gate to the specific fallback transition it caused.

There is also a progression defect. `NOMINATE_NEXT_ROUTE` skips only candidates that “have already been attempted under the current effective requirement.” A candidate skipped because dispatch admission was not positive has not been attempted. Therefore, after an external-gate fallback, the original blocked candidate remains “unattempted” and can be selected again by the same ordering rule unless an implementation invents an additional consumed/skipped state. That makes replay susceptible to re-selection loops or implementation-specific skip bookkeeping.

**Required repair:** add immutable event-level external-gate provenance to the fallback/route-decision lineage and define a deterministic candidate-consumption state for externally blocked-but-not-dispatched candidates (for example, an explicit nomination/skip record or a route-candidate disposition set). `NOMINATE_NEXT_ROUTE` must operate on that exact replay-retained state, not only on dispatched attempts.

**Affected acceptance IDs:** `C2-204`, `C2-221`, `C2-228`.

### C2ROUTE-B04 — Requirement downgrade conflicts with the candidate-revisit rule for the same provider candidate

C2.03 correctly forbids in-place mutation of `R` and requires a distinct authorized `R'`. It also defines candidate consumption relative to the “current effective requirement,” which implies a candidate previously attempted under `R` may be newly eligible under `R'`.

However, the next sentence states that a candidate may be revisited **only** through `NOMINATE_SAME_ROUTE_REATTEMPT`, while `NOMINATE_SAME_ROUTE_REATTEMPT` is explicitly required to preserve the **same effective requirement**. These rules conflict for the valid case:

```text
candidate A attempted under R
trusted authority supplies distinct R'
compatible(R', A, S) == true
```

`NOMINATE_NEXT_ROUTE` appears to allow A because A has not been attempted under R', but the global revisit rule forbids selecting A as NEXT_ROUTE. `NOMINATE_SAME_ROUTE_REATTEMPT` cannot be used because it may not change the effective requirement. No other route action applies an authorized downgrade to the same candidate.

The contract therefore does not define a total transition relation for an authorized `R -> R'` downgrade.

**Required repair:** explicitly define how an authorized downgraded requirement becomes the effective requirement and how candidate attempt identity is keyed across requirement revisions. Either permit a deterministic same-candidate/new-requirement nomination distinct from SAME_ROUTE_REATTEMPT, or explicitly forbid it and justify/encode that restriction. Add a dedicated acceptance vector for the same-candidate `R -> R'` case.

**Acceptance coverage:** this exact adversarial case is not represented by a dedicated C2.03 obligation; the repair must add one. It also requires reconciliation with `C2-228` and `C2-229`.
